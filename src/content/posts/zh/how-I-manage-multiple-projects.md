## 一个 Agent，加一个够强的 Harness，就够了？

现在很流行一种说法：模型够强、harness 够好，一个 agent 就能把产品从需求做到上线。拆任务这种事，交给 Claude Code 或 Codex 自己去拆就行。

我以前也这么信。后来发现，这个说法把“能不能做完”和“做出来的是不是你要的”两个问题混在了一起。
harness 确实越来越强。但单靠智力依旧没办法解决结构层面的难题。

一个 agent 从头干到尾，有三个结构性的盲点，换更强的模型也消不掉：

- **我觉得我能行。** 需求里没写清楚的边界，她会按自己的习惯默默定掉。甚至，模型偶尔还会悄悄“摸鱼”。
- **开发人员就是写BUG的人。** 和人类一样，你让开发测试自己的代码是永远检测不出BUG的。毕竟对需求的理解完全一样。
- **沉浸在自己的艺术里的产品经理。** 产品经理知道按钮为什么在那儿，所以永远不会觉得那个按钮难找。

这三条和模型聪不聪明无关，毛病出在同一双眼睛既当运动员又当裁判。解法也就不在更强的 harness，在流程：谁出题，谁答题，谁验收，谁拍板。

> 虽然没有具体的统计数字，但闯出大祸的一般都是最顶尖的模型，我被坑过最惨的一次就来自 Fable 5.1。

## 一个人带好几个产品，为什么会心里没底

我同时负责好几个产品，且只有我一个人真正在乎这些玩意最后变成什么样。

**认知债，像信用卡。** 自己写代码，相当于现金支付：写一行懂一行，理解是顺带付清的。而交给 agent，就是产品先到手，理解什么的账单出了再说。时间在走，利息在滚。产品越多，欠款越多，在项目间跳来跳去，脑子里的那个版本早已过期。

agent 产出的速度，永远比人类读的速度快。靠读代码是还不上认知债的。

**编排税，像过路费。** 为了填补单 agent 的短板，很多人会在工作流中拆出一堆角色：分析师、PM、架构师、开发、QA。每传一手，信息就丢一点；每过一道关，就交一笔 token。角色拆得越细，交接就越多，协调者的上下文就越肿，花在“你说完了吗、轮到我了吗”这种仪式上的算力也越多。最终产物与最初构想的差别也就越大。

两笔账是互相拉扯的：不拆，认知债越滚越大；乱拆，编排税把你压垮。**所以真正的问题不在“拆不拆”，在“拆在哪里”。**

## 降维拆解：生活里早就有的五个老办法

我的 workflow 叫 graph-workflow，只有四个角色和一个 Python 脚本。它的核心并不新鲜，大部分上班族天天在用。

**闸机！**

&#91;embedded content: graph-workflow 全景 · 四个角色、一道闸机、一个保险柜\]


### 1. 包工头只有一个

传话游戏里人越多，最后一句越离谱。所以 PM、架构师、编排者和代码审查我只给一个角色，叫 Main，用最强的模型，来与用户在窗口里交互。

拆出去的角色为三件事：要一双没被污染的新眼睛（Tester、Punk），要并行干活（Coder），还要给 Main 的上下文减负。

角色之间不聊天，防止他们相互寒暄浪费上下文，只提供有页数预算的文件。

### 2. 需求确认单

装修工人不会问你插座装多高，他会按自己的习惯装。agent 也一样：需求含糊的地方，她通常会默默替你决定。

所以开工前有一张确认单（Gate 1）。Main 把每条需求按 7 个类别过一遍：阈值、中途插入、重复触发、跨越时间点、计数口径、运行环境、失败恢复。并且像一个拥有绝佳向上管理技巧的牛马一样，给出选项和建议，“决定”那一栏必须用户亲手填。不填？下一步就进行不了了哦。

这些决定会被逐字抄进每个任务的 brief，脚本会比对，一个字都不能改。确保后面所有角色的输入，都是原始需求。

### 3. 严苛的审计

如果考生自己出题、自己改卷，分数就没有意义。可是让 agent 写完代码再补测试，结果就是这样：测试会照着代码的样子长，把代码的错误逻辑也一起继承下来。

我的 Tester 在代码存在之前就出卷，只看 brief。卷子分两部分：明题交给 Coder 当例题，暗题锁进仓库外面的保险柜，只在考试那一刻才解封。

外加**一套暗题只用一次**。没有通过测试的题目发放给 Coder；Tester 再出一套和以前都不一样的案例。就算 Coder 偷看了，她看到的也只是一套作废的案例。如果三轮还过不了，任务便挂起，交由用户评审。

&#91;embedded content: 每个任务的验收循环 · 暗题用完即作废\]


### 4. 口味刁钻的“客户”

艺术家总会沉浸在自己的艺术世界里。做产品的 agent 也看不见外面的世界。

Punk 是我流程里最重要的角色，她的工作就是唱反调。她只读 PRD，不读代码，在桌面和手机宽度下截图，在用户的角度去审视产品：主任务能不能完成？PRD 答应的功能都实现了吗？有没有奇怪的东西冒出来？流程反不反直觉？她最多提 5 条反对意见，每条带截图、代价和替代方案，还要逐项对照一张常见体验问题清单：危险操作有没有确认，状态在页面外面看不看得见，文字看不看得清，刷新一下会不会丢东西之类的。

她和 Main 唱对台戏是设计好的。Main 写计划、审代码，两样都做得越好，越看不见计划自己的盲区。Punk 冷启动进来，没有任何上下文，只知道自己现在是“用户”。

### 5. 地铁闸机，不是“请勿逃票”的告示

讲得极端点，prompt 里的规则就是用来打破的。

所以凡是能机械检查的，我都交给 `gw.py`：规定每个任务的九个步骤必须按顺序走，Coder 只能改 brief 列出的文件，明题必须字节级不变，每条需求最多 1 道明题 2 道暗题，测试不允许去读源代码里的字符串，文档有字数预算。

用户只在两个节点出现：开工前签确认单（Gate 1），每个里程碑的验收测试（Gate 3）。中间单个任务的验收（Gate 2）属于 Main 和脚本，无需用户判断。

## 踩过的坑怎么复盘

经验要能传到下一个 session，业务直觉要随迭代自动复利，不能每次靠用户重新输入，也不能靠抽卡的概率。

公路上的事故黑点，立一块警示牌是最便宜的办法，但也最不管用。真正有效的是护栏和改道。写进共享配置的一段文字就是警示牌：agent 读到了也未必照做，条目一多还会互相矛盾，甚至上下文一多就完全被无视。

CHANGELOG 基本就是一本踩坑记录，而且每个坑都修成了护栏。

比方说：

| 坑 | 护栏 |
| --- | --- |
| pre-commit hook 拒了提交，合并命令忽略失败，照样报 MERGED，接着关任务删掉了 worktree，一个任务的代码就这么凭空消失 | 提交失败就停；任务分支没有新提交就拒绝合并 |
| 模板推荐用 junction 共享 `node_modules`，强制删除 worktree 时把主目录的依赖一起清空了 | 关任务前先解除所有链接再删 |
| 两个并行任务同时收尾，互相覆盖了对方的状态文件 | 保存前重读，只写自己那个任务 |
| 一批测试去抓源代码里的字符串，没有测行为本身 | 脚本拒收读源码的测试 |
| 做 UI 的 agent 总忽视用户体验 | 变成 Punk 必查的清单 |

这些坑有一个共同点：都不在需求里明确指出，且都出在 agent 和环境的交界处，比如 hook、链接、并发、Windows 的 PowerShell。Tester 管代码对不对得上 brief，Punk 管产品对不对得上需求，“流程和现实对不对得上”只有脚本在管。所以 agent 总在意想不到的地方坑你一把，这类坑没法提前写好，只能事后接住、快速分拣。

我的分拣原则是：**能修成护栏的，就别立警示牌。** 从上往下挑第一个放得下的地方：

| 坑的类型 | 去哪 | 确定性 |
| --- | --- | --- |
| 流程或环境出错 | 脚本里的检查 | 护栏 |
| 产品行为回归 | 用过的暗题转成永久回归测试 | 护栏 |
| agent 又悄悄替你做了决定 | 确认单加一个类别或一句追问 | 闸口，开工前拦 |
| 反复出现的 UI 毛病 | Punk 必查清单 | 闸口，里程碑拦 |
| 这个项目的技术或业务怪癖 | 组件文档里的 Gotchas，用到该组件时才读 | 警示牌 |
| 跨项目的技术栈坑 | 所有 agent 共用的知识库 | 警示牌 |
| 只会发生一次 | 不搬，记一笔就行 | — |


## 这不是银弹

说完好处，说点不好听的。

- **编排税是真的。** 多一个角色，就多一次交接、一份文件、一轮等待。这套流程比一个 agent 一口气写完慢得多，也贵得多。只能换来“你可以不读代码”。
- **小活不值得。** 很小的需求，留下 Main 和需求确认单即可，最多加上 Punk。
- **流程会滋生文书。** 角色一多，文档就暴涨，认知债只是从代码换成了自然语言。所以我给每种文档都设了类型和页数上限，由脚本来数。（偶尔也会收到模型关于纸不够的抱怨）
- **结构和措辞都不保证赢。** 关于多 agent 系统为什么失败的研究里，改 prompt 和改拓扑都有帮助，哪个更有效因系统而异，许多作者自己的结论是“有用，但不够”。哪里反复出错，就改能修好它的最小一处。

## 总结

1. **Harness 决定能不能做完，流程决定做的是不是你要的。** 即使下一代模型又便宜又强，我也不认为这个问题就能完美解决。
2. **出题、答题、验收，必须是三双不同的眼睛。** 测试先于代码写，暗题只用一次。
3. **人类只需现身两次。** 开工前签确认单，里程碑验收测试。代码可以一行不读，但需求确认单必须认真审视：认知债不会消失，但可以压缩到一个文档里。
4. **能写成代码的规则，就别写成 prompt。** Prompt 只是“提示”。
5. **给每个产品安排一个专门唱反调的角色。** 当没有第二个人在乎一个产品时，就造一个。
6. **拆分要算账。** 加流程比加智力划算。
