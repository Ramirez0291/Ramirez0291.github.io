## 一个 Agent，加一个够强的 Harness，就够了？

现在很流行一种说法：模型够强、harness 够好，一个 agent 就能把产品从需求做到上线。拆任务这种事，交给 Claude Code 或 Codex 自己拆就行。

我以前也这么信。后来发现，这个说法把“能不能做完”和“做出来的是不是你要的”混成了一个问题。harness 是越来越强了，可有些毛病出在结构上，光靠智力解决不了。

一个 agent 从头干到尾，有三个盲点，换更强的模型也消不掉：

- **我觉得我能行。** 需求里没写清楚的边界，她会按自己的习惯默默定掉。模型偶尔还会悄悄“摸鱼”。
- **开发人员就是写 BUG 的人。** 跟人一样，让开发测自己的代码，永远测不出 BUG，因为她对需求的理解和写代码时一模一样。
- **沉浸在自己艺术里的产品经理。** 产品经理知道按钮为什么在那儿，所以永远不会觉得那个按钮难找。

这三条和模型聪不聪明无关，毛病出在同一双眼睛既当运动员又当裁判。所以解法不在更强的 harness，在流程：谁出题，谁答题，谁验收，谁拍板。

> 我没有统计数字，只是体感：闯大祸的往往是最顶尖的模型。我被坑得最惨的一次就来自 Fable 5.1。

## 一个人带好几个产品，为什么会心里没底

我同时负责好几个产品，而且只有我一个人在乎这些玩意最后变成什么样。

**认知债，像信用卡。** 自己写代码相当于现金支付：写一行懂一行，理解顺带就付清了。交给 agent，就是产品先到手，理解的账单以后再说。时间在走，利息在滚。产品越多，欠得越多，在项目之间跳来跳去，脑子里那个版本早就过期了。

agent 产出的速度永远比人读的速度快，靠读代码还不上这笔债。

**编排税，像过路费。** 为了补单 agent 的短板，很多人会在工作流里拆出一堆角色：分析师、PM、架构师、开发、QA。每传一手，信息丢一点；每过一道关，交一笔 token。角色拆得越细，交接越多，协调者的上下文越肿，花在“你说完了吗、轮到我了吗”这种仪式上的算力也越多，做出来的东西离你最初想要的也越远。

两笔账互相拉扯：不拆，认知债越滚越大；乱拆，编排税把你压垮。**所以问题不在“拆不拆”，在“拆在哪里”。**

## 生活里早就有的五个老办法

我的 workflow 叫 graph-workflow，只有四个角色和一个 Python 脚本。里面的招数一点也不新鲜，上班族天天在用。

**闸机！**

&#91;embedded content: graph-workflow 全景 · 四个角色、一道闸机、一个保险柜\]


### 1. 包工头只有一个

传话游戏里人越多，最后一句越离谱。所以 PM、架构师、编排者和代码审查，我全交给一个角色，叫 Main。她用最强的模型，在窗口里和用户对话。

其他角色拆出去只为三件事：要一双没被污染的新眼睛（Tester、Punk），要并行干活（Coder），还要给 Main 的上下文减负。

角色之间不聊天，省得互相寒暄浪费上下文，只递有页数上限的文件。

### 2. 需求确认单

装修工人不会问你插座装多高，他按自己的习惯装。agent 也一样，需求含糊的地方，她通常会默默替你决定。

所以开工前有一张确认单（Gate 1）。Main 把每条需求按 7 个类别过一遍：阈值、中途插入、重复触发、跨越时间点、计数口径、运行环境、失败恢复。她还得像个深谙向上管理的牛马，把选项和建议都摆好，但“决定”那一栏必须用户亲手填。不填？那下一步就别想了哦。

这些决定会被逐字抄进每个任务的 brief，脚本逐字比对，一个字都不许改。这样后面每个角色拿到的，都是原始需求。

### 3. 考生不能自己出题

考生自己出题、自己改卷，分数就没有意义。可让 agent 写完代码再补测试，就是这么回事：测试照着代码的样子长，把代码里的错误逻辑也一并继承了。

我的 Tester 在代码还不存在的时候就出卷，只看 brief。卷子分两部分：明题交给 Coder 当例题，暗题锁进仓库外面的保险柜，考试那一刻才解封。

还有一条：**一套暗题只用一次**。没过的题发给 Coder 去改，Tester 再出一套从没用过的。就算 Coder 偷看了，她看到的也只是一套作废的卷子。三轮还过不了，任务挂起，交给用户评审。

&#91;embedded content: 每个任务的验收循环 · 暗题用完即作废\]


### 4. 口味刁钻的“客户”

艺术家总沉浸在自己的艺术里，做产品的 agent 也看不见外面的世界。

Punk 是我流程里最重要的角色，她的工作就是唱反调。她只读 PRD，不读代码，在桌面和手机宽度下截图，站在用户的角度看产品：主任务能不能完成？PRD 答应的功能做了没有？有没有冒出奇怪的东西？流程反不反直觉？她最多提 5 条反对意见，每条带截图、代价和替代方案，还要逐项对一张常见体验问题清单：危险操作有没有确认，离开页面后状态还看不看得到，字看不看得清，一刷新会不会丢东西，诸如此类。

她和 Main 唱对台戏是故意的。Main 写计划、审代码，两样做得越好，越看不见计划本身的盲区。Punk 冷启动进来，什么上下文都没有，只知道自己现在是“用户”。

### 5. 地铁闸机，不是“请勿逃票”的告示

说得极端点，prompt 里的规则就是用来打破的。

所以凡是能机械检查的，我都交给 `gw.py`：每个任务的九个步骤必须按顺序走，Coder 只能改 brief 里列出的文件，明题必须字节级不变，每条需求最多 1 道明题 2 道暗题，测试不许读源代码里的字符串，文档有字数上限。

用户只在两个节点出现：开工前签确认单（Gate 1），每个里程碑做验收测试（Gate 3）。中间单个任务的验收（Gate 2）归 Main 和脚本管，用户不用操心。

## 踩过的坑怎么复盘

经验得能传到下一个 session。业务直觉要随着迭代自己复利，不能每次靠用户重新交代，也不能靠抽卡。

公路上的事故黑点，立块警示牌最便宜，也最不管用，管用的是护栏和改道。写进共享配置的一段文字就是警示牌：agent 读到了也未必照做，条目一多还会互相打架，上下文一长干脆就被无视了。

我的 CHANGELOG 基本就是一本踩坑记录，每个坑都修成了护栏。比如：

| 坑 | 护栏 |
| --- | --- |
| pre-commit hook 拒了提交，合并命令无视失败照样报 MERGED，接着关任务、删 worktree，一个任务的代码就这么凭空没了 | 提交失败就停；任务分支没有新提交就拒绝合并 |
| 模板推荐用 junction 共享 `node_modules`，强制删 worktree 时把主目录的依赖一起清空了 | 关任务前先解除所有链接再删 |
| 两个并行任务同时收尾，互相覆盖了对方的状态文件 | 保存前重读，只写自己那个任务 |
| 一批测试去抓源代码里的字符串，根本没测行为 | 脚本拒收读源码的测试 |
| 做 UI 的 agent 总忽视用户体验 | 变成 Punk 必查的清单 |

这些坑有个共同点：需求里都没写，而且都出在 agent 和环境的交界处，比如 hook、链接、并发、Windows 的 PowerShell。Tester 管代码对不对得上 brief，Punk 管产品对不对得上需求，“流程和现实对不对得上”只有脚本在管。agent 总会在意想不到的地方坑你一把，这类坑没法提前写好，只能事后接住，赶紧分拣。

我的分拣原则是：**能修成护栏的，就别立警示牌。** 从上往下，挑第一个放得下的地方：

| 坑的类型 | 去哪 | 确定性 |
| --- | --- | --- |
| 流程或环境出错 | 脚本里的检查 | 护栏 |
| 产品行为回归 | 用过的暗题转成永久回归测试 | 护栏 |
| agent 又悄悄替你做了决定 | 确认单加一个类别或一句追问 | 闸口，开工前拦 |
| 反复出现的 UI 毛病 | Punk 必查清单 | 闸口，里程碑拦 |
| 这个项目的技术或业务怪癖 | 组件文档里的 Gotchas，用到该组件时才读 | 警示牌 |
| 跨项目的技术栈坑 | 所有 agent 共用的知识库 | 警示牌 |
| 只会发生一次 | 不搬，记一笔就行 | — |


## 这不是银弹

说完好处，说点不好听的。

- **编排税是真的。** 多一个角色，就多一次交接、一份文件、一轮等待。这套流程比一个 agent 一口气写完慢得多，也贵得多，换来的只有一件事：你可以不读代码。
- **小活不值得。** 很小的需求，留下 Main 和确认单就够了，顶多再加个 Punk。
- **流程会滋生文书。** 角色一多，文档就暴涨，认知债只是从代码搬到了自然语言里。所以我给每种文档都定了类型和页数上限，让脚本去数。（偶尔会收到模型抱怨纸不够用。）
- **改结构、改措辞，都不保证赢。** 研究多 agent 系统为什么失败的论文里，改 prompt 和改拓扑都有帮助，哪个更有效看系统，不少作者自己的结论是“有用，但不够”。哪里反复出错，就改能修好它的最小一处。

## 最后

1. **Harness 决定能不能做完，流程决定做的是不是你要的。** 就算下一代模型又便宜又强，我也不觉得这个问题会自己消失。
2. **出题、答题、验收，得是三双不同的眼睛。** 测试先于代码写，暗题只用一次。
3. **人只需要露面两次。** 开工前签确认单，里程碑做验收。代码可以一行不读，确认单必须认真看：认知债不会消失，但可以压进一份文档里。
4. **能写成代码的规则，就别写成 prompt。** Prompt 只是“提示”。
5. **给每个产品安排一个专门唱反调的角色。** 没有第二个人在乎这个产品，那就造一个。
6. **拆分要算账。** 加流程比加智力划算。
