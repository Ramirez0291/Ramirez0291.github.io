## 一、悄悄地就完成了

在迭代我的开源多 Agent 工作流项目 **[graph-workflow](https://rami0291.com/notes/graph-workflow/)** 的过程中，我发现了一件事：

当需求文档或业务规则里存在歧义时，大模型几乎不会停下来问“老板，这里有两条路，按哪个走？”。它会顺着自己的训练习惯，悄悄替你选一条写进代码或方案里，并且全程一声不吭。

迭代早期，我做了一个基准实验：让不同的 Agent 配置去构建同一个专注计时器应用（Flow Timer），并在需求里故意预埋了 4 处业务歧义（比如倒计时剩不到两分钟时触发离开检测怎么算、中途手动暂停再恢复怎么累计离开时间、10 秒宽限期内切回来怎么计数）。

| 实测指标 | 多 Agent 工作流（Claude Code） | 单 Agent（Claude Code） | 单 Agent（Codex） |
| --- | --- | --- | --- |
| 有效构建耗时 | 约 101 分钟 | 约 10 分钟 | 约 15 分钟 |
| 4 处预埋歧义被主动提问 | **0/4** | **0/4** | **0/4** |
| 4 处预埋歧义被测试钉住 | 4/4 | 2/4 | 2/4 |
| 6 类常见 UX 缺陷带病上线 | 抽检 4 类中 0 类 | 6/6 | 6/6 |
| 测试代码 : 产品代码 | 约 5:1 | 0.8:1 | 0.9:1 |

（注：多 Agent 工作流在 Codex 上跑到一半就没跑下去——防御性内容堆得太多，工程上已经崩了——所以没有列进表里。）

我发现，AI 明明注意到了这些预埋歧义（多 Agent 工作流甚至把 4 处全写进了测试），但向我提问的次数是零。而且不同模型“静默拍板”的方向还不一样：单 Agent 的 Codex 把 10 秒宽限期内的闪回算作一次打断；单 Agent 的 Claude 则从最后一次键盘输入（而不是切走标签页的那一刻）开始计算两分钟离开计时。两边选的逻辑都能自圆其说，但谁都没告诉我。

把这个现象放进数字化基础薄弱的中小企业的业务里，后果很严重。这类企业八成的核心规则根本不在文档里，全在老员工嘴上（“这种包装磕碰算不算质量问题要看客户是谁”“月底最后一天下单能不能锁旧价格”）。你让 AI 接管工单或写内部工具，遇到这些没写下来的空白地带，AI 不会报错，也不会请示，它会面不改色地用一套“硅谷平均常识”替你把板拍了。它的输出读起来通顺合理，事实核查（Fact-check）也查不出任何幻觉，但就是违背了公司的习惯。

而在我试图治这个毛病时，又撞上了别的问题。

为了逼 Agent 在动手前把歧义吐出来，我在后续版本中给流程加了一道硬关卡：开工前必须拿每个需求去过一遍固定的“七类边界扫描表”（阈值、中途插入、重复触发、时间边界、计数规则、运行环境、失败恢复），并由用户逐项决断，否则 `gw gate 1` 脚本会拒绝放行后续任务。

结果，把这套规则放进真实的多里程碑项目（先是一个 3 个里程碑、39 个任务的数据看板重做，接着是在既有产品上加自动更新队列任务）之后，Agent 直接从“闷头不吭声”跳到了另一个极端：**拿鸡毛蒜皮的伪问题疯狂刷 KPI。**

既然流程奖励“把边界列全”，到了任务规划阶段，PRD 里的边界表一路膨胀到了近百行：其中绝大多数根本不是需要人来拍板的业务歧义，而是去翻一下现有的代码调用方、看一眼数据库 Schema，或者套用一条基本常识就能定下来的工程细节。

讽刺的是，它在 92 行细枝末节上找我请示，却在最该开口的生产动作上再次选择了“静默”：团队明明早就在决策记录里写过服务端不支持热重载，但直到 6 个任务、45 个子会话全部跑完、代码都合进主分支，Agent 们加班到晚上十点半时，主 Agent 才想起来问一句“能不能重启生产容器”。那时我早已下线了。

最新版里，我把固定套模板的“七类边界扫描”砍了，换成了三条更符合真实业务治理的规矩：

1. **先查家底，不准伸手要饭**：要求主 Agent 在列歧义之前，必须先去读现有的调用方、数据库 Schema 和配置文件。旧代码里已经有答案的，老老实实照着做，不准拿来烦人。（可恶，最后不还是和能工智人一样去读代码。）
2. **用一条“默认容错底线”砍掉 80% 的伪歧义**：在模板里直接写死默认原则（比如“遇到坏数据跳过并记录报告；只有不可逆的操作才硬停”）。凡是能套用默认原则的工程边界一律不准上表，只有会改变用户拿到什么结果、且没有先例的开放业务选择，才准提上来让老板拍板。
3. **把生产环境的批准提前到开工前（Gate 1）**：像“合并后重启服务”这种有风险但必做的标准动作，在开工前的 `Approvals` 表里连同回滚方法一次性签字授权；如果没获批，收尾时必须把“服务仍在跑旧代码”贴在状态页最显眼的第一行。

对企业的教训是一以贯之的：不把隐性规则和默认底线写下来，AI 就会替你“静默决定”；但你要是只会用死板的表格去逼它提问，它就会用 90 多条废话把审批人淹死，然后继续在最要命的地方漏掉真问题。

## 二、快不等于省

顺着 `graph-workflow` 的实战迭代记录往下看，还能看到技术债和认知债是怎么在“测试全绿”的假象下慢慢累积起来的。

先说说为什么 `graph-workflow` 的适用对象和实验里都没有 GPT 系列的多 Agent 协作。在 Codex 上跑基准实验时：

- 代码里被 Agent 偷偷夹带了两百多行防御性代码，包括 11 个莫名其妙的状态标志、两个版本计数器、三重重置逻辑。
- 有一个原本要求的功能，被 Agent 悄悄删掉了。
- 调用 git 一直报错后，Agent 自己发明了一套快照方案，直接把本地仓库撑大了十倍以上。
- 同一个里程碑一口气吐出了 **66 个文件、大约 24,000 字** 的流程文档（全是 GPT 标志性的防御套话）。

在 Codex 上跑多 Agent 工作流时，光是负责审查的 Agent 在 145 次审查里就烧掉了 **1,290 万个 Token**。

而 Claude Code 在三个里程碑里总共吞掉了超过 **10 亿个 Token**，其中评审和规格检查占了驱动成本的 65%。

为了堵住这些窟窿，新版本要求 Coder 必须在交接单里填一张“新增防御代码申报表（`Defenses added`）”；给任务书（`brief`）设了**硬性字数上限**；为了不让测试被写代码的 Agent 带偏，把写测试的 Tester 完全隔离在代码库之外，只准它看任务书盲写测试，再锁进外部的密封测试集（held-out tests）。

结果到了实战（产出 743 行产品代码和 3,819 行测试代码），这几道机械关卡集体给我上了一课：

- **“自报防御代码”形同虚设**：6 份交接单的 `Defenses added` 栏整整齐齐写着 `none`。但评审 Agent 直接去翻代码 diff 时，却在 5 个任务里揪出了至少 7 处明显多余的防御守卫，并当场删掉。让 AI 自己申报技术债是没用的，得靠独立视角直接审 diff（所以 v0.8 我把强制自报表砍了）。
- **硬字数上限逼出了“压字死循环”**：任务 43 在写回一轮循环记录后超出了字数上限，结果 Agent 为了把字数压回线内过关，把那份任务书来回改了 **24 次**。
- **不看家底的“盲写测试”全在给自己挖坑**：实战中一共发生了 4 轮正式返工，全都是因为测试或任务书自己写错了，返工期间 Coder 的产品代码一行都没改过。最离谱的一个任务里，因为 Tester 没看现有的数据库 Schema，直接对着一张没有主键的表写 `INSERT OR REPLACE`，还去读一个根本不存在的列；3 组密封测试挂掉，全是测试自己的 Bug，为此白白烧掉了 11 个测试和评审子会话。
- **玩具夹具里跑绿的 159 个测试，漏掉了 4 个真缺陷**：所有自动化测试都是在新建的空数据库和一两个假模板上跑的，一路全绿。等到主 Agent 最后拿真实生产数据库的副本把页面拉起来测试，炸出 4 个大坑：只读连接撞上没迁移的旧库，页面直接打不开；加载真实环境里的 11 个模板慢到发指；入队后列表不刷新；还有一个按钮写成了别的语言。

难怪在 [METR 做的随机对照试验](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)里，资深开源开发者用上 AI 辅助后，实际完成任务的速度反而慢了 19%，但事后填问卷时，大家却一致觉得自己快了 20%。

用 Agent 写代码和写方案，很像刷信用卡赊账购物：东西当下就拿到手了，爽感拉满，但你对系统的理解（认知债）一分钱都没还。很多人以为多加几道机械审批关卡就能高枕无忧，我的教训是：机械关卡卡住的大多是形式，Agent 会花掉大把 Token 去迎合你的形式；而决定线上生死的那些事，必须在真实数据副本和运行界面上用肉眼检查。

最后说一句：对小项目或者小修小补来说，用单 Agent 配上“拍板开放业务选择”和“不看源码、只看真实运行界面的验收”，成本比复杂的多 Agent 工作流低十倍，效果却差不多。只有到了跨月演进的大项目，才值得上这套带状态机的工作流，而且测试和评审必须直接踩在真实的数据 Schema 和历史数据副本上。
