## 1 つの Agent、それに十分に強い Harness があれば、それで十分か？

今、モデルが十分に強く、harness が十分に良ければ、1 つの agent で要件から本番環境までの製品を完成できるという説が流行っている。タスクを分割するようなことは Claude Code や Codex に任せて、自動的に分割させればいいというわけだ。

昔日の私もそう信じていた。後になって気づいたのだが、この説は「完成できるかどうか」と「完成したものがお前の求めたものかどうか」を一つの問題として混ぜてしまっている。harness はどんどん強くなっているが、ある種の問題は構造に由来するもので、知能だけでは解決できない。

1 つの agent が最初から最後まで担当すると、より強力なモデルに切り替えても消えない 3 つの盲点がある：

- **我は大丈夫だと思う。** 要件に明確に書かれていない境界については、彼女は自分の習慣に従ってひっそりと決めてしまう。モデルが時々こっそり「さぼる」こともある。
- **開発者はバグを書く人だ。** 人間と同じように、開発者に自分のコードをテストさせると、彼女の要件に対する理解とコード作成時の理解が全く同じだから、バグは決してテストでは見つからない。
- **自分の芸術に没入しているプロダクトマネージャー。** PM はボタンがなぜそこにあるのかを知っているので、そのボタンが見つけにくいとは決して感じない。

この 3 つは、モデルがどれだけ賢いかとは無関係だ。問題は、同じ眼で同時に選手でもあり、審判でもあるところにある。したがって、解決策は、より強い harness ではなく、プロセスにある：誰が問題を出すのか、誰が答えるのか、誰が検証するのか、誰が最終決定を下すのか。

> 統計数字はないが、体感としては：大失敗を招くのはしばしば最高峰のモデルだ。私が最もひどい目に遭わされたのは Fable 5.1 からだ。

## 1 人で複数の製品を担当するのに、なぜ不安感があるのか

複数の製品を同時に担当しているが、最後にこれらがどうなるかに関心を持つのは私だけだ。

**認知債は、クレジットカードのようなものだ。** 自分でコードを書くことは現金で支払うのと同じだ：1 行書いたら 1 行理解でき、理解は同時に清算される。agent に任せると、製品はまず手に入り、理解の請求書は後回しだ。時間は経つ、利息は膨らむ。製品が多いほど、借金は多くなり、プロジェクト間を飛び回ると、頭の中のそのバージョンはとっくに古くなっている。

agent の出力速度は常に人間の読む速度より速く、コードを読むだけではこの借金は返済できない。

**オーケストレーション税は、通行料のようなものだ。** agent の短所を補うため、多くの人がワークフローにさまざまな役割を導入する：アナリスト、PM、アーキテクト、開発者、QA。伝達するたびに情報が失われ、門を通すたびにトークンが消費される。役割を細かく分ければ分けるほど、ハンドオフが増え、コーディネーター上下文が膨らみ、「お前が言い終わったか、今度は俺の番か」というような儀式に費やされる計算力も増え、できあがるものは最初に望んでいたものからさらに遠のく。

この 2 つの帳簿は互いに引っ張り合う：分割しなければ、認知債はますます膨らみ；無茶に分割すれば、オーケストレーション税が君を潰す。**したがって、問題は「分割するかしないか」ではなく、「どこで分割するか」にある。**

## 生活の中にすでに存在する 5 つの古い方法

私の workflow は graph-workflow と呼ばれ、4 つの役割と 1 つの Python スクリプトしかない。その中の手法は全く新しくなく、サラリーマンが毎日使っているものだ。

**改札機だ！**

### 1. 工事責任者は 1 人だけ

伝言ゲームで人が多いほど、最後の一文は思い違いになる。だから PM、アーキテクト、オーケストレーター、コードレビュー、すべてを 1 つの役割に任せる。Main と呼ぶ彼女は、最強のモデルを使い、ウィンドウ内でユーザーと対話する。

他の役割を分ける理由は 3 つだけだ：汚染されていない新しい眼（Tester、Punk）が必要だ、並行して作業する必要がある（Coder）、そして Main の上下文を軽減したい。

役割同士は会話しない。互いに挨拶して上下文を無駄にしないためだ。ページ数に上限のあるファイルだけを渡す。

### 2. 要件確認書

改装工は、コンセントをどれだけ高く取り付けるかを聞かない。彼は自分の習慣に従って取り付ける。agent も同じで、要件が曖昧な部分では、通常、ひっそりとお前の代わりに決めてしまう。

そのため、開始前に確認書（Gate 1）がある。Main は各要件を 7 つのカテゴリで確認する：閾値、途中挿入、繰り返しトリガー、時間点を超える、カウント基準、実行環境、失敗復旧。彼女はまた、上方管理に精通した馬のように、オプションと推奨事項をすべて配置する必要があるが、「決定」欄はユーザーが手で記入する必要がある。記入しない？なら次のステップはお前には無理だ。

これらの決定は、各タスクの brief に逐語的にコピーされ、スクリプトは逐語的に比較する。1 文字の変更も許されない。このようにして、後の各役割が受け取るのは常に元の要件だ。

### 3. 受験者は自分で問題を出題できない

受験者が自分で問題を出題し、自分で採点すれば、点数は意味がない。agent にコードを書かせてから後でテストを補うというのはこういうことだ：テストはコードの形に合わせて成長し、コード内の誤ったロジックもまた一緒に継承される。

私の Tester はコードがまだ存在しないときに問題を出す。brief を見るだけだ。問題は 2 つの部分に分かれている：明題は Coder に例題として与え、暗題はリポジトリの外の金庫に鍵をかけ、試験の時に初めて解放する。

それに：**1 つの暗題セットは 1 回だけ使用される。** 不合格の問題は Coder に修正を与え、Tester が新しく未使用のセットを出す。Coder が盗み見したとしても、彼女が見るのは無効な問題セットだけだ。3 ラウンド合格しなければ、タスクは保留され、ユーザーレビューに渡される。

### 4. 味にうるさい「顧客」

芸術家は常に自分の芸術に没入している。製品を作る agent も外の世界は見えない。

Punk は私のプロセスで最も重要な役割だ。彼女の仕事は異を唱えることだ。彼女は PRD だけ読み、コードは読まない。デスクトップと携帯の幅でスクリーンショットを撮り、ユーザーの視点から製品を見る：メインタスクを完了できるか？PRD で約束した機能は実装されたか？奇妙なものが出ていないか？プロセスは直感に反していないか？彼女は最大で 5 つの異議を唱え、各々スクリーンショット、コスト、代替案を伴わせ、また一般的なユーザー体験の問題チェックリストに対して逐項対応する：危険な操作に確認はあるか、ページを離れた後状態は見えるか、文字は見えるか、リフレッシュで何か失われないか、など。

彼女が Main と対立するのは意図的だ。Main が計画を書き、コードをレビューし、両方をうまくやるほど、計画自体の盲点が見えなくなる。Punk は冷たくスタートしてやってくる。上下文がなく、自分が今「ユーザー」であることだけを知る。

### 5. 地下鉄の改札機は「乗り越し厳禁」の掲示板ではない

極端に言えば、prompt の中のルールは破られるためのものだ。

だから機械的にチェックできるものは、すべて `gw.py` に任せる：各タスクの 9 つのステップは順番に進まねばならない。Coder は brief に列挙されたファイルだけを変更できる。明題はバイトレベルで変わらなければならない。各要件は最大 1 つの明題と 2 つの暗題。テストはソースコード内の文字列を読めない。ドキュメントは単語数に上限がある。

ユーザーは 2 つのポイントにだけ現れる：開始前に確認書に署名（Gate 1）、各マイルストーンで受け入れテストを実施（Gate 3）。中間の個別タスクの受け入れ（Gate 2）は Main とスクリプトが管理し、ユーザーは心配する必要がない。

## 踏んだ穴をどう復盤するか

経験は次のセッションに伝える必要がある。ビジネスの直感は反復とともに複利しなければならず、毎回ユーザーに説明してもらうか、ガチャに頼ることはできない。

路上の事故ホットスポットは、警告看板を立てるのが最も安く、最も効果がない。管用なのは手すりと迂回路だ。共有設定に書かれたテキストは警告看板だ：agent が読んでも従わないかもしれない。項目が多いと互いに喧嘩をする。上下文が長いと完全に無視される。

私の CHANGELOG は基本的には踏んだ穴の記録簿で、各穴は手すりに改造されている。例えば：

| 穴 | 手すり |
| --- | --- |
| pre-commit hook がコミットを拒否した。マージコマンドが失敗を無視してそれでも MERGED と報告する。その後タスクを閉じて worktree を削除すると、1 つのタスクのコードはこのようにして消えてしまう。 | コミット失敗で停止。タスクブランチに新しいコミットがなければマージを拒否。 |
| テンプレートが `node_modules` を共有するために junction を使用することを推奨した。worktree を強制削除するときに、メインディレクトリの依存関係も一緒に削除されてしまった。 | タスクを閉じる前に、すべてのリンクを解除してから削除。 |
| 2 つの並行タスクが同時に終了し、互いに相手の状態ファイルを上書きした。 | 保存前に再読み込み。自分のタスクだけ書く。 |
| テストのバッチがソースコード内の文字列を取得し、行動をテストしていない。 | スクリプトがソースコードを読むテストを拒否。 |
| UI を作る agent は常にユーザー体験を無視する。 | Punk の必須チェックリストになる。 |

これらの穴に共通点がある：すべて要件に書かれていず、すべて agent と環境の交界にある。例えば hook、リンク、並行、Windows の PowerShell だ。Tester はコードが brief に対応しているか管理し、Punk は製品が要件に対応しているか管理する。「プロセスと現実が対応しているか」を管理しているのはスクリプトだけだ。agent は常に予期しない場所で君を坑にはめる。このタイプの穴は事前に書いておくことはできず、事後に受け取り、素早く分類する必要がある。

私の分類の原則は：**手すりに改造できるなら、警告看板を立てるな。** 上から下へ、最初に当てはまるところを選ぶ：

| 穴のタイプ | どこに | 確実性 |
| --- | --- | --- |
| プロセスまたは環境エラー | スクリプト内のチェック | 手すり |
| 製品動作の回帰 | 使用済みの暗題を永続的な回帰テストに変換 | 手すり |
| agent がまたこっそり決定を下した | 確認書にカテゴリまたは追加質問を追加 | 改札口、開始前に遮断 |
| 反復的な UI バグ | Punk の必須チェックリスト | 改札口、マイルストーン遮断 |
| このプロジェクトの技術またはビジネスの奇癖 | コンポーネントドキュメント内の Gotchas。該当コンポーネント使用時に読む | 警告看板 |
| クロスプロジェクト技術スタックの穴 | すべての agent が共有するナレッジベース | 警告看板 |
| 1 回だけ発生する | 移動しない。記録するだけ | — |


## これは銀の弾ではない

メリットを言い終えたから、耳に心地よくないことを言おう。

- **オーケストレーション税は本物だ。** 役割が 1 つ増えると、ハンドオフが 1 つ増え、ファイルが 1 つ増え、待機ラウンドが 1 つ増える。このプロセスは、1 つの agent が一気に完成させるより、はるかに遅く、はるかに高い。代わりに手に入るのは 1 つのことだけだ：お前はコードを読まなくてもいい。
- **小さい仕事はそれだけの価値がない。** 非常に小さな要件の場合は Main と確認書を残すだけで十分だ。最大でも Punk を追加すればいい。
- **プロセスは書類を繁殖させる。** 役割が多いほど、ドキュメントは爆増する。認知債は単にコードから自然言語に移されるだけだ。だから各種ドキュメントに型とページ数の上限を設定し、スクリプトに数えさせる。（時々モデルが紙が足りないと文句を言うのを聞く。）
- **構造を変える、措辞を変える。どちらも勝利は保証されない。** 複数 agent システムがなぜ失敗するのかについての論文では、prompt を変えることとトポロジーを変えることの両方が役立つ。どちらがより効果的かはシステム次第で、多くの著者自身の結論は「有用だが十分ではない」だ。どこで繰り返しエラーが発生するか、それを修正できる最小の場所を変更する。

## 最後に

1. **Harness は完成できるかどうかを決定し、プロセスは完成したものがお前の求めたものかどうかを決定する。** たとえ次世代モデルが安くて強力だとしても、この問題が自動的に消えるとは思わない。
2. **問題を出す、答える、検証する。これは 3 つの異なる眼でなければならない。** テストはコードの前に書かれ、暗題は 1 回だけ使用される。
3. **人間は 2 回だけ姿を現せばいい。** 開始前に確認書に署名し、マイルストーンで検証を実施する。コードは 1 行も読まなくていいが、確認書は真摯に見なければならない：認知債は消えないが、1 つのドキュメントに詰め込むことはできる。
4. **コードとして書けるルールは prompt に書くな。** Prompt は単なる「ヒント」だ。
5. **各製品に反対意見を唱える専門の役割を割り当てる。** この製品に関心を持つ 2 番目の人がいなければ、1 つ作ってしまえ。
6. **分割は計算する必要がある。** プロセスを追加することは知能を追加することより経済的だ。
