又一家公司把十年没清理过的共享网盘直接接进了知識ベース。

その中には、`商品説明_最終版_v3_絶対に変更しません.xlsx` という名前のスプレッドシートが数百個あって、同じ商品が ERP、EC バックオフィス、営業チームの Excel の中で 3 つの違う名前で呼ばれている。今年 Agent のニュースが津々浦々に行き渡ったのを見て、月曜の朝礼で経営陣は決断を下した：「弯道超車を狙おう。全員 AI に All-in だ」。

二ヶ月後、AI が動き始めた。毎日、シングルデーのセール後の倉庫爆発みたいなドライブから、ミリ秒単位の速度で検索を行い、ブロードキャストアナウンサー並みの自信満々の語調で、三年前からすでに廃止された商品パラメータを引用して、カスタマーサービスの問い合わせに答えている。

そして老朽化した業務システムには API が一個も無いから、営業チームの毎日の仕事は、ウェブチャットボックスを開いて、顧客の要件を貼り付けて、AI が何か吐き出すのを待って、またそれを手作業で ERP に貼り戻す（運が悪けりゃ 2 行くらい漏す）。

これが私が言う「データ沼地での全裸ランニング」だ。

心当たりあるか？同じような事故が業界中で量産中だ。[RAND のレポート](https://www.rand.org/)によると、AI プロジェクトの 80% 以上が最終的に失敗していて、第一の原因は最初から問題の定義が間違っていたこと、次点は適切なデータがないことだ。[S&P Global の統計](https://www.spglobal.com/market-intelligence/en/news-insights/research/2025/10/generative-ai-shows-rapid-growth-but-yields-mixed-results)によると、AI パイロットの大部分を放棄することを決定した企業の比率が、2024 年の 17% から 2025 年の 42% へと一気に上昇している。[Gartner の調査](https://www.gartner.com/en/newsroom/press-releases/2025-02-26-lack-of-ai-ready-data-puts-ai-projects-at-risk)では、63% の組織が AI 対応のデータ管理能力を持っていないか、持っているか不確実だという結果が出ている。Gartner はこれに基づいて、2026 年末までに、利用可能なデータが不足している AI プロジェクトの 60% が直接キャンセルされると予測している。

日本の状況も似たようなものだ。[IPA《DX 動向 2025》](https://www.ipa.go.jp/digital/chousa/discussion-paper/tbl5kb0000006bvm-att/dx2025_activities_for_driving_growth.pdf)によると、日本企業のおよそ 8 割がデジタル変革（DX）を推し進めているが、成果が見えたと言い張れるのは 6 割だけだ。100 人以下の中小企業に至っては、DX を推してるのは 46.8% しかなく、企業の 85.1% が人手不足を叫んでいる（ちなみに連中は DX 人材には法定最低賃金しか払おうとしない）。

多くの経営者の心の中に、一つの侥幸な考え方がある：デジタル化は苦しくて遅い。道作りをスキップして、一気に二段跳びで飛び越えられないかなあ。

こういった考え方を出し抜くために（そして毎回同じ説明を繰り返す手間を省くために）、私はオープンソースのオンライン自己評価ツールを作った。名前は **[AINativeBench（AI ネイティブ双軸診断）](https://rami0291.com/ainativebench/)** だ。メインラインは 16 問あって、5 分で終わる。

## 一、「AI をどれだけ使っているか」だけを見ると人を殺す理由

市場にある成熟度テストのほとんどが「何個アカウント買ったのか」「何トークン使ったのか」と聞いている。だが俺の見方では、デジタル化の基礎から切り離して AI 普及率を語るのは、流砂の上に何階建てたかを数えるようなもんだ。

[AINativeBench](https://rami0291.com/ainativebench/) では、2 本の軸を使った。X 軸は **デジタル化成熟度** で、デジタル化の 4 本柱を借りて、データが各システム・各プロセス間で通じてるか（接続性）、システム間にインターフェースはあるか（プログラマビリティ）、プロセスが自動閉ループできるか（自律性）、現場の従業員がデータを調整できるか（エンパワーメント）を見る。Y 軸は **AI 採用と融合度** で、エンタープライズアカウントインフラ、知識ベースの成熟度、ダイアログボックス非依存設計、本番介入の深さ、コンプライアンスガードレール、そして「AI 税」防止のための手戻り率測定に至るまでをカバーしている。

さらに、この診断は AI ネイティブビジネスは考慮しない。

2 本の軸を 60 点で切ると 4 つのクワドラントができる（右上が AI ネイティブ先導区、右下が堅実蓄積区、左下が太古の化石区、左上がもっとも危ない **幻覚裸奔区**)。

さらに、4 つの自己陶酔防止メカニズムを用意した：

**基礎不安定ディスカウント線**
AI の攻撃性がデジタル化基盤を 10～20 点上回るだけで、ダッシュボードが黄色くなって警戒モードに入る。20 点以上を上回ると、「基礎不安定」と判定されて、ペナルティ公式が発動される。
俺の考えでは、企業が裸奔区にあるとき、ボロボロの基礎の上に AI にさらに 1 点でも金をぶっこむと、状況はもっと悪くなる。

**ガードレール上限と相互チェック**
多くの管理層が設問に回答するときに自分たちに高得点をつけるのが好きだ。コンプライアンスガードレールの中に「従業員 AI 使用ガイドライン」すらなければ、本番業務介入の深さでどんなに積極的に選んでも、システムはその項目を強制的に 50% で上限固定される。同時に、バックエンドは自動的に自己矛盾した回答の 4 つのグループを検出する：

- 「AI がバックエンド業務フローに静かに統合されている」とのことだが、コアシステムは閉じた黒箱のレガシーソフトだ。インターフェースがない――AI の出力はどうやってシステムに書き戻されるんだ？（また従業員が苦しむのか？）
- 「全社的に統一されたダイナミック知識源」とのことだが、相変わらず手作業で Excel を同期してる。システムすら繋がってないのに、知識ベースのデータは誰が毎晩真夜中に同期してんだ？
- 「AI が本番業務に介入している」とのことだが、基本的な自動化ロールバックもない。
- 「AI が本番業務に介入している」とのことだが、エンタープライズアカウントも買ってない。

**証拠空心円**
スコアリング項目ごとに、以下のようなチェックボックスが付いている：「提示可能な証拠がある（ポリシードキュメント、バックエンド スクリーンショット、監視データ）」。証拠にチェックを入れなかった項目は、保守的なスコアを計算するとき、バックエンドが自動的に 1 段階ダウングレードする。その後、逆パターン自己診断で対応するレッドゾーンに命中すれば、さらに 1 段階ダウングレードする。マトリックスグラフの上では、自己評価は青い実心円だ。証拠の見直し後のスコアは空心円だ。

**ボスの注意喚起ハロー効果**
ほとんどの中小企業はボスの一言で決まるから、「経営者がデジタル人材を重視しているか」と聞くのは無意味だ（どのボスも自分が重視してないなんて認めない）。俺が用意したのは 6 つの事実だけを見るイエス・ノー問題だ：年間予算に独立した予算枠があるか（部門間で「なぜ俺たちの予算で」と揉めないように）？KPI に書き込まれた責任者の名前があるか？ボス本人が過去 1 ヶ月間、毎週 AI を使ってて、その場で見せられるか？過去 1 年間に、少なくとも 1 つのポジションの職務記述書を書き直したか？パイロット失敗で責任追及されなかった先例があるか？ボスが 3 ヶ月の出張から帰ってきても進められる書かれた路線図があるか？

## 二、9 つの「サイバー企業病」と 2 つの疑似デジタル化

経営者が自分たちを当てはめやすいように、[AINativeBench](https://rami0291.com/ainativebench/) の中で、一般的なアンチパターンを 16 の企業パーソナリティに体系化した。「幻覚裸奔区」に陥った企業は、だいたい以下の 9 つの中に自分たちの影を見つけられるはずだ：

| 企業パーソナリティ | 典型的症状 | 踏んづけたレッドゾーン |
| --- | --- | --- |
| **幻覚疾走の狂信者** | マスターデータすら揃ってないのに、大規模言語モデルの出力を神聖視する。幻覚が AI より酷い | ゴミ入ゴミ出 |
| **データ裸泳ぎの冒険家** | エンタープライズアカウントを買わず、マスキング保護も設定せず、AI が顧客のコアデータを本番に直結 | Shadow AI と責任の黒い穴 |
| **人肉インターフェースの運搬工** | 老朽 システムはプログラム不可能、従業員は毎日チャットボックスと業務システムの間で人間のクリップボード | 人肉 API |
| **電子文書の彫刻職人** | 紙ベースの承認をオンラインで 1 対 1 で移す。承認段階はそのまま。PDF をデジタル化と勘違い | ルールは脳内、静黙決定を起動 |
| **サイバー拾い屋のハムスター王** | 10 年掃除されてない共有盤を丸ごと RAG に流し込む。AI は自信満々で廃止済み規則を引用 | 出典のある誤り |
| **スクリーン押しボタンの操り人形** | RPA でマウスクリックをシミュレートして API 化のつもり。ウェブフロントエンドが改版されたら全体麻痺 | トランザクション回滚なし、本番事故 |
| **トークン焚却炉の司炉工** | 報告では「日産 500 文案」「トークン呼び出し 100 万超」とだけ披露。下流の後始末に費やされた時間は計算しない | 帳面上の繁栄。ROI 計算不可 |
| **PoC 炼獄の船人** | 1 年に 8 つのパイロット。コストを計算しないし実運用システムに接続しないから、常に「いい感じ」「本番には乗らない」 | デモで停滞。運用誰もいない |
| **単点通電のサイバー酋長** | 全社のプロンプト、スクリプト、データパイプラインが 1 人の従業員の脳内。その人が離職＝ダウン | 単点依存、ガバナンス欠如 |

以前、「経営陣はデジタル化されたと思ってるが、現場の仕事は毎日 Excel の細工」と言われていた。この「疑似デジタル化」を俺は 2 つのカテゴリに分ける：

一つは **電子文書の彫刻職人** だ。OA とオンラインワークフロー導入したが、やったのはオフラインの列をスクリーンに移しただけ。いくら以内で承認できるか、どの常連客は特別に通せるか、ルールは全部承認者の頭の中で、条件ステートメントとして記述されたことがない。

もう一つは **人肉インターフェースの運搬工** だ。ちゃんとした ERP と CRM を買ったが、ソフトは 10 年前の閉じたブラックボックス設計のままだ。API がまったくないか、あってもべき等性とサンドボックスすらない（Agent のタイムアウトで 1 回再試行したら、重複発注が勝手に成立する）。

前者の医学的処方は、人の脳から承認条件を抽出してコードルールに書くこと。後者の処方は、高頻度操作に対して認証とべき等キー付きの本物の API を追加することだ。

## 三、4 つの爆発メカニズム：幻覚より怖いのは「静黙決定」

通常、裸奔企業のリスクを 1 本の直線で描ける、と考えてる：「データが構造化されてない → AI に大量の脏データを入れる → AI が幻覚を起こす」。
だが俺の見方では、この線は、もっと危険なものを見落としている。

基盤が薄い企業に無理矢理 AI を入れた爆発プロセスを分解すると、4 つのメカニズムが同時に動いてる。

### 1. 汚いデータが「出典のある誤り」を製造する

[OpenAI の 2025 年 9 月論文](https://openai.com/index/why-language-models-hallucinate/)は指摘している：モデルが幻覚を起こすのは、事前訓練の目的と現在のベンチマークが「確実でなくても推測しろ」と奨励しているせいであって、自社データがどれだけきれいかは関係ないって。たとえ教科書レベルにきれいなデータでも、拒答メカニズムのないシステムは相変わらず編造する。

では、汚いデータをクリーンアップしなくても大丈夫か？

ベクトル検索（RAG）は「意味的に最も似たスニペット」を検索するだけで、どのドキュメントが「最新で最も権威的か」なんて気にしない。共有ドライブに 5 つのバージョンの規則が並存してて、モデルが 2022 年から廃止されてる返金基準を検索して、真顔で答えて、ファイルリンクまで付ける。これは純粋な捏造より怖い。この「出典があり、オリジナル文書」の答えで、真実と嘘が混じってるのを識別できるのは、そのビジネスに非常に詳しい人だけだ。

誰かが手抜きして「検索スキップしてしまえ、何百ページもの資料を超長コンテキストにぶっこむ」ってやったら、別の穴に落ちちゃう。[Chroma の Context Rot 実験](https://www.beri.net/learning/chroma-context-rot-report)は 18 の最先端モデルをテストして、例外なく：入力が長いほど、性能劣化がひどい；意味的に近い干渉情報が濃いほど、モデルの脳がさらに混乱する。

### 2. 従業員が人肉 API に堕落する

システムがプログラム可能なインターフェースを持たなければ、Agent はチャットボックスでしかしゃべられない。

多くの企業が興奮して十数個の内部アシスタント Bot を構築して、従業員に固定テンプレートにビジネス情報を貼り付けさせて、結果を貼り戻させる。ウィンドウ間の人手による移動のたびに AI が節約した時間を食い潰し、たまに新しいコピー・ペーストエラーをもたらし、最悪なのはシステムログが全くないことだ。だから Bot を増やせば増やすほど、現場の従業員は辞めたくなる。

### 3. Shadow AI と甩り落とせない法律黒鍋

企業が使いやすい正規ツール提供しないか、一刀両断で禁止したら、従業員は定時に帰るために個人の無料アカウントで顧客名簿と契約書をこっそり流し込む。[IBM の 2025 年データ漏洩レポート](https://newsroom.ibm.com/2025-07-30-ibm-report-13-of-organizations-reported-breaches-of-ai-models-or-applications,-97-of-which-reported-lacking-proper-ai-access-controls)が試算した：調査対象の 20% の組織すでに Shadow AI でデータ漏洩経験済み；Shadow AI 高頻度使用企業がやられたら、平均さらに 67 万米ドル善後費用；AI 関連侵入経験済み全組織の 97% が AI アクセス制御ゼロだった。

事後に LLM に責任をなすりつけられると思うなよ。著名な [Moffatt v. Air Canada 事件](https://www.americanbar.org/groups/business_law/resources/business-law-today/2024-february/bc-tribunal-confirms-companies-remain-liable-information-provided-ai-chatbot/)では、エアカナダのカスタマーサービスチャットボットが、存在しない遺族返金ポリシーを作っちゃった。その後エアカナダは「チャットボットは独立した法律実体で、企業はその声明に責任を持たない」と主張──仲裁廷はこれを退け、企業に判決を下した。[デロイト・オーストラリア](https://www.techradar.com/pro/deloitte-forced-to-refund-aussie-government-after-admitting-it-used-ai-to-produce-error-strewn-report)も政府に提出したレポートが AI 生成で誤りだらけだったから、公式で謝罪して返金を余儀なくされた。2027 年 12 月 2 日までに、[EU AI Act](https://secureprivacy.ai/blog/eu-ai-act-digital-omnibus-the-new-high-risk-ai-deadlines-after-council-approval)附件 III 高リスクシステムのコンプライアンス義務が正式発効する。「AI が出力する 1 語 1 語は、すべてデプロイ企業の公式約束として扱われる」、これが世界的な法律デフォルトになる。

### 4. 静黙決定

ルールが書かれてない箇所で、AI は立ち止まって聞かない――こっそり決断を下す。詳細は：[graph-workflow の開発とエンジニアリング実践記](https://rami0291.com/notes/brawl-with-graph-workflow/)参照。

## 四、三年間の苦しい DX を待たずに、AI でデジタル化に追いつく方法は？

ここまで読んで「幻覚裸奔区」にいるボスはこう聞きたくなるだろう。AI を全部止めて、コンサル企業に頼んで 3 年間をかけて伝統的な DX を完成させてから、また AI に手を出さないといけないのか？

そこまで絶望することはない。私の提案は、AI を対外的なコア生産フローから撤退させ、その力を切り替えて、最も苦しい「データ化への補習」をするのを手伝わせることだ。ただし、確定的なコードと人工審査でその行動を厳しく制御しなければならない。

外部データはこの道が通じることを証明しているが、一気にできるとは期待するな。2025 年[MDPI に発表された請求書抽出の研究](https://www.mdpi.com/2079-9292/14/11/2145)は GPT-4o が実際のビジネス請求書を処理するパフォーマンスをテストした。単一フィールドの精度は 97.15% に達し、見た目は素晴らしいが、単据全体が完全に間違っていない「ドキュメントレベルの精度」に計算すると、85.29% に落ちた（おおよそ 7 枚に 1 枚の請求書に誤りが含まれている）。日本横浜市は約 4,500 ページの PDF 法規を RAG が呼び出せる構造化データに変換し、動作確認後、公式な結論も「継続的な人工調整が必須」だ。

知識ベースの蓄積（Y2 と X1 に対応）という点では、**[LLM-Wiki](https://rami0291.com/notes/why-llm-wiki-fits-sme-knowledge-bases/)**という低コストの手法があるが、完璧ではない。

Karpathy が 2026 年 4 月に提案したアーキテクチャを借用しており、従来の RAG との最大の違いは、**知識を整理する手間な仕事を「資料取り込み時（Ingest-time）」に置き、「質問時（Query-time）」ではない**というものだ。

1. **`raw/` オリジナルレイヤ（読み取り専用、決して変更しない）**：会議録音の書き起こし、契約原本、操作マニュアル、シニア従業員のインタビューを、ここに原状のまま固定し、企業唯一の真実の源とする。
2. **`_proposals/` 提案バッファレイヤ**：新しい資料が入るたびに、10 から 15 個の知識ページを連動して変更する必要があるかもしれない。LLM は正式なライブラリを直接変更することはできず、まず提案エリアに PR を提出し、業務責任者が目を通して確認してから、正式な `wiki/` にマージできる。
3. **`wiki/` コンパイルレイヤと `Lint` 週間スキャン**：Wiki に記載されたすべての結論は、`raw/` のオリジナル文書にハイパーリンクで指し示す必要がある。毎週 `Lint` スキャンスクリプトを実行し、矛盾した記述、期限切れのルール、孤立したページを特に抽出する。

前述の「マスターデータのあちこちでの言い分」と「沈黙のうちに決定する」という問題を治すため、この Wiki を導入する際に 3 つのルールがある。

- **実体ページは型番または唯一 ID で命名する必要がある**。意味が似ているからといって同じものではない。ID で命名することで、みんなにマスターデータをまず揃えることを強制される。
- **実時データはデータベースに留め、散文には編集しない**。在庫、価格、注文状態は ERP または kintone にそのまま留め、Agent は MCP または API を通じてリアルタイムで照会する。
- **具体的なケースを使ってシニア従業員の話を詰めていく**。「我々の返品ルールは何ですか」と聞いてはいけない。彼自身も完全にはまとめられない。先月の実際の作業指示を持って、「あのパッケージ破損の返品、どう判定した？」と聞く。インタビュー録音を `raw/` に入れ、LLM がルールのドラフトにまとめさせ、シニア従業員に署名確認させる。来週 `Lint` がスキャンして出したロジックの漏れが、次回インタビューの質問リストになる。

（もちろん、この方法にも明確な限界がある。保守の負担は消えておらず、「人が書く」から「人が審査する」に変わっただけだ。また、各テーマはおよそ 100 個のオリジナル資料、数百ページの Wiki の規模内が最適で、それ以上になると、またはきめ細かいドキュメント権限が必要な場合は、やはり正直に Confluence または Notion のような成熟した SaaS を使う必要がある。）

## 五、裸奔企業の三段階止血ロードマップ

[McKinsey 2026 年グローバル AI 調査](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-state-of-ai)には冷めた数字がある。AI が至る所で使われているが、EBIT（利息税引前利益）への貢献が見える企業は 37% に過ぎず、高パフォーマンスと言える企業は約 6% である。この 6% の企業に共通点がある。彼らは AI を古いプロセスに貼り付けたアドオンとして扱わず、AI を中心に仕事フローと職位を再設計したのだ。

もし [AINativeBench](https://rami0291.com/ainativebench/) でテストして、自分の Y 軸が既に X 軸より 20 ポイント以上高いことに気づいたり、18 項目の反パターン自己診断で大量にヒットしたりした場合、来年はこれら 3 つの段階に従い、まず出血を止め、その後補習、最後に権限委譲ができる（各段階の移行前に、双軸診断を再度実施）。

### 第一段階（0–3 カ月）：止血と整理

- 管理層は別々に診断を行う。ボス、IT 責任者、業務責任者がそれぞれ独立して [AINativeBench](https://rami0291.com/ainativebench/) を 1 回行い、答えを照合しない。最大の相違のある何問かをテーブルに出して、はっきり議論する。
- コア生産フローから補助的な位置を撤回する。価格変更、払い戻し、対外顧客の約束に関わるステップは、すべて「AI が下書き草案を出し、人工が送信する」というシャドウモードに戻す。
- シャドウ AI を採用する。みんなが個人的に使っている無料アカウントを把握し、個人版より使いやすい企業グレードのソリューションを購入する（データが学習に使用されないという合意を署名し、SSO と監査ログをセットアップする）。1 ページで読める《内部 AI 使用ガイドライン》を配布する（すべてをシステムプロンプトに詰め込んで AI を劣化させないこと）。
- 1–3 個の高頻度試験的運用をロックダウンする。各試験的運用は、指名された責任者、**リワーク率（Rework Rate）と単位当たりのコスト**を含む KPI、および明確な退出ストップロス条件に結びつけられなければならない（「30% の生成時間を節約しながら、40% の時間をクリーンアップに費やす」ことを防ぐ）。
- デフォルトの容許度ベースラインを定め、決定権のある業務選択のみを限定する。AI にエンジニアリング上の細部を数十個並べて許認可を求めさせない。まずグローバルなデフォルト原則を固定する（例えば「不正データはスキップして報告を記録し、非可逆操作のみが停止をトリガー」）。Agent に既存コードとデータベーススキーマを最初に確認させる。顧客体験を変える業務の曖昧性で先例がないものだけがリスト化され、業務方が書面署名で決定する。決してモデルに推測させない。

### 第二段階（3–6 カ月）：AI で基礎を補う

- まず商品と顧客という 2 つのマスターデータテーブルを確立する。企業全体で唯一のコーディングを定める。大規模言語モデルを使って歴史的な古いテーブルの不正なコーディングを整列させるのを手伝わせることができるが、すべてのマッピング関係は人工確認後にのみデータベースに入力できる。
- LLM-Wiki または Google フルスイートなどのツールを使用して暗黙の知識を蓄積させる。`raw/` は読み取り専用を厳守し、Agent は `_proposals/` のみを提出し、実際のケースを持ってシニア従業員にインタビューし、頭の中の業界ルールを追跡可能な Markdown に変える。
- 実データの上に構築されたゴールデンテストセット（50–200 個の実ビジネス問題）を構築する。テストは既存の本番スキーマを最初に読み込む必要があり、匿名化された実データの履歴コピーで実行する必要がある（空のデータベースとおもちゃデータ上で自己満足しない）。一部を「密閉テストセット」として外部に固定し、Prompt を変更するたびまたはモデルを切り替えるたびに回帰テストを実行する。
- RPA をステップバイステップで本当の API に置き換え、コード diff を直接審査する。高頻度のビジネスアクションに、独立したサービスアカウント、テストサンドボックス、べき等キー、構造化エラー報告を備えた API を補足する（MCP に直接変換して Agent が呼び出せる）。AI 自身が技術負債をリストアップして申告することを期待しない。CI と独立した審査で、コード diff に対して防御的なコードを直接削減し、実データコピーで実際のページパフォーマンスをテストする。

### 第三段階（6–12 カ月）：ハード境界内での権限の再委譲

- 5 つの条件が揃うまで Agent をアップロードしない。流程に唯一の権威データ源、継続的に基準を達成するテストセット、監査可能なフルアクション、コードレベルのハード境界（金額上限、アクション許可リスト、ワンクリック回滚）、および人工否決権が同時にある場合のみ、Agent は本番管理を再開できる。
- Agent に「オンボーディング登録」を行う。企業全体の Agent レジストリテーブルを作成し、各ボットの用途、オーナー、ツール権限範囲、評価スコア、定期的なオフライン化メカニズムを明記し、離職した従業員が残した幽霊 Agent が管理者トークンを持って後ろで裸奔することを防ぐ。
- ジョブタイトルを再度書き直し、スキルを保持する。少なくとも 1 つのポジションの職務記述書を正式に再度書き直す。同時に、定期的な「AI なしのブラインドテスト演習」を設計して、チームが業務判断力を完全に失い、確認キーをクリックするだけのゴム印になることを防ぐ。

## 最後に自分を叩く

この記事を書いて、外部研究と `graph-workflow` の実測データを改めて見直す過程で、[AINativeBench](https://rami0291.com/ainativebench/) の現在のバージョンにも 3 つの不正確な点があることに気づいた。

1. ツール内の「幻覚裸奔区」への処方は「すぐに降速して撤退し、予算を接続と API 補足に転用する」と書いただけで、撤退させられた AI の計算能力が何をすべきかを皆に言うのを忘れていた。
2. エンタープライズ知識ベースの満点基準に、RAG、LLM Wiki、ロングコンテキストが同等と並列して記載してしまった。Chroma のロングコンテキスト退化実験と我々独自の比較を組み合わせると、この 3 つは全く等価ではない。
3. 象限の 60 点合格ラインと $Y - X > 20$ のラインは、現在のところ、私が直感で定めた経験的閾値だ。
