## 序文：目を背けられない 3 つの幻想

> **「動くからといって、本番に出せるわけではない。」**
> チームの誰の頭にも「入力検証（Input Validation）」「サーバー側での認証・認可（Server-side Auth）」「冪等性」といった概念がなければ、最初の Prompt を書いた時点で、プロジェクトの結末は決まっている。

🔍 いくつかの事例を見てみよう。

* **「AI にちゃんと伝えたのに、それでも指示に背いた！」**
  SaaStr 創業者の Jason Lemkin が Replit Agent で Vibe Coding を試した際、チャットで「コードは凍結中。本番環境には絶対に触るな」と繰り返し指示していたにもかかわらず、AI は 1,000 社以上の企業データが入った本番データベースを空にしてしまった。（[eWeek の報道](https://www.eweek.com/news/replit-ai-coding-assistant-failure/)、2025 年 7 月）

* **「開発予算を 5,000 万から 3 万に削減した！」**
  SNS には、こうした胸の躍るコスト削減神話があふれている。だが、その先を問う人はいない。アーキテクト、プロダクトマネージャー、プロジェクトマネージャー、DBA、セキュリティ顧問を全員「合理化」したあと、システムの停止、データの丸見え状態、アーキテクチャの行き詰まりのツケは誰が払うのか。

* **「機能はどこ？ AI は完成したと言っていなかった？」**
  AI は、あなたが説明した新機能の開発も本番への反映も終わったと告げる。ところが git の履歴をくまなく探しても、該当するコミットが見つからない。

**根本の問題は、自然言語の Prompt を「強制力のある制約（Hard Constraint）」だと思い込み、環境そのものの分離や、データベースへの読み取り専用アクセス権限（IAM）が何なのかを理解していないことだ。**

## 失敗する Vibe Coding に共通する 4 つの特徴

私たちは、多くの Vibe Coding プロジェクトが「3 日で爆速リリース」から「1 週間で壮絶に崩壊」へ転げ落ちるのを見てきた。どれも例外なく、次の 4 つの深い落とし穴にはまっている。

### 1. 「ハッピーパス（Happy Path）」という幻想

Demo では驚くほど滑らかに動く。UI は洗練され、主要な操作も一気に最後まで通る。しかし中をのぞくと、コードにあるのは理想的な条件下での処理だけで、**ネットワークのタイムアウト、同時読み書きによる競合、決済コールバックのリトライ、返金処理の逆方向の状態遷移、特殊文字の入力といったエッジケース（Edge Cases）がまったく考慮されていない**。実際のユーザーが少しでも想定から外れた操作をすれば、データの不正な上書きや、画面が真っ白になるクラッシュに直結する。

### 2. フロントエンドとバックエンドの防御が形だけになっている

本来はサーバー側（Server-side）で強制すべき権限チェックを、AI が気軽にフロントエンドのコンポーネントへ書いてしまう。厳重に管理すべき API キーや強い権限を持つデータベース認証情報が、クライアントの JS バンドルにハードコードされ、外から丸見えになる。たとえば、2025 年 3 月に「手書きコードゼロ」をうたった [Enrichlead](https://vibegraveyard.ai/story/enrichlead-vibe-coded-saas-shutdown/) は、公開から数日で攻撃を受け、最終的に閉鎖した。また、Supabase の行レベルセキュリティ（RLS）を設定しなかったために、他のユーザーのデータが見えてしまうアプリも数多い。

数字は嘘をつかない。

* セキュリティ企業 **GitGuardian** が 2026 年 3 月に公開した[レポート](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/)によると、Claude Code を使ってコミットされたコードのシークレット漏えい率は **3.2%** で、GitHub の全公開コミットの基準値（1.5%）の 2 倍以上だった。問題はツールだけにあるわけではない。Agent によるコミットがあまりに滑らかに進むことで、操作する人がシークレット漏えいのリスクを見落としやすくなる。これは私自身も経験している。
* セキュリティ企業 **Escape.tech** が 2025 年 10 月、公開されている Vibe Coding アプリを [**5,600 件以上スキャン**](https://escape.tech/blog/methodology-how-we-discovered-vulnerabilities-apps-built-with-vibe-coding/)したところ、**2,000 件超の脆弱性**、**400 件超の露出したシークレット**、**175 件の実際の個人情報（PII）漏えい**が見つかった。しかも、これは受動的なスキャンで得られた下限の推定値にすぎない。

### 3. モグラたたき式の「パッチ無限ループ」

コードが数千行規模を超えると、機能 A を直しただけで、ほとんど必ず無関係な機能 B が壊れる。自動テスト（Unit/E2E Test）の支えも、明確なモジュール境界もないため、技術を知らない開発者は**「エラーメッセージの運び屋」**になるしかない。ターミナルの赤い文字を機械的に AI へ貼り付け、ある箇所を直す代わりに別の箇所を壊す新しいコードを受け取り、バグが再発し続けるループの中で、忍耐と Token を使い果たす。

### 4. 「局所では筋が通り、全体では支離滅裂」なブラックボックスのアーキテクチャ

コードは別々の会話ターン、ときには別々のモデルによって断片的に生成され、つなぎ合わされている。そのため、関数をひとつずつ見ればもっともらしくても、全体としては論理が矛盾する。同じ業務エンティティが 3 つのモジュールで 3 種類のデータ構造を持ち、共通のユーティリティ関数を定義した直後に、別のファイルで同じものが再発明される。最後には、コードベースは書いた本人すら直視したくないクソコードのブラックホールへと急速に崩れていく。

## なぜ Vibe Coding は制御不能になるのか

問題を「今のモデルはまだ賢くないから」で片付けるなら、見る方向を完全に間違えている。複雑な開発で Vibe Coding が失敗するのは、大規模言語モデルの根本的な仕組みと、ソフトウェアエンジニアリングの客観的な法則が組み合わさった結果だ。

### 1. 報酬関数のずれ：「動く」と「正しい」は同じではない

ある研究者は、**「Coding Agent の最適化目標は、コードを動かすこと（Make code run）であって、安全にすること（Make code safe）ではない」**と[指摘している](https://towardsdatascience.com/the-reality-of-vibe-coding-ai-agents-and-the-security-debt-crisis)。
大規模言語モデルはコードを生成するとき、エラーを消し、その場で期待されている見た目を満たすために、最も抵抗の少ない道を選びがちだ。複雑な権限チェックを省く、環境変数の設定をハードコードで代用する、広すぎる例外処理でエラーを握りつぶす。どれも Demo を最速で動かすための「近道」になる。[Veracode の 2026 年 3 月の評価](https://www.veracode.com/blog/spring-2026-genai-code-security/)では、主要な大規模言語モデルが生成するコードの構文上の正解率はすでに **95%** を超えているのに、安全性テストの通過率は **55%** 前後で停滞している。

### 2. コンテキストのずれと注意の希薄化（Lost in the Middle）

歴史ある「クソコードの山」に向き合うときは、どれほど大胆で優秀な人間のエンジニアでも、チームに加わってから数週間は依存関係を整理し、最初にどこへ手を入れるべきかを見極める必要がある。
一方、大規模言語モデルは、非常に長いコンテキストを扱うときに情報を見失い、注意が薄まる性質を持つ。プロジェクトが膨らむにつれ、全体の状態、暗黙の業務ルール、過去の妥協の間で整合性を維持できなくなる。規模が大きくなるほど、有効なコンテキストの信号対雑音比が下がり、生成されるコードの品質は急落する。

### 3. 「技術的負債」から致命的な「認知的負債（Cognitive Debt）」へ

従来の開発で納期を急いで背負うのは**技術的負債**だ。人間のエンジニアは、自分のコードがどれほどひどいかを把握していないかもしれないが、頭の中にはシステムのメンタルモデル（Mental Model）があり、あとからリファクタリングできる。対して、純粋な Vibe Coding で背負うのは**認知的負債**だ。考えてコードを書く過程を飛ばすため、人間のチームは内部のデータの流れや状態の境界をまったく理解していない。システムが壊れたとき、問題箇所を突き止めることすらできない。

### 4. ソフトウェアエンジニアリングの役割とガバナンスの欠如

ソフトウェアエンジニアリングは、単に「要件をコードの構文に翻訳する」ことではない。アーキテクトはシステムを進化させる範囲と障害対策の最低ラインを定め、プロダクトマネージャーとプロジェクトマネージャーは要件を整理し、取消・返金など逆方向の処理まで成立させる。DBA とセキュリティエンジニアは、データ資産とコンプライアンス上の一線を守る。
Vibe Coding を盲信するチームは、予算を大きく消費する一方で最も重要でもある人間の頭脳を「合理化」したあと、「コードが生成された＝製品を本番に出せる」と無邪気に考えてしまう。だが、**AI は極めて強力な増幅器だ。エンジニアリングを理解する専門家の手にあれば生産性を増幅する。エンジニアリングへの畏れを欠く素人の手にあれば、混乱とリスクを 10 倍の速さで増幅するだけだ。**
