## 一、静かにこなしてしまう

オープンソースの多 Agent ワークフロープロジェクト **[graph-workflow](https://rami0291.com/notes/graph-workflow/)** を反復処理する過程で、私はある事実を発見した：

要件ドキュメントまたはビジネスルールに曖昧性が存在する場合、大規模言語モデルはほぼ確実に「上司よ、ここに二つの道がある、どちらを行くべきか？」と立ち止まって聞かない。それは自分の訓練習慣に従い、静かにお前の代わりに一つの選択肢を選んでコードまたはプランに書き込み、全プロセスを通して完全に口を閉ざしたままである。

反復の初期段階で、私は基準となる実験を行った：異なる Agent 構成で同じ焦点タイマーアプリケーション（Flow Timer）を構築させ、要件の中に意図的に 4 つのビジネス曖昧性を埋め込んだ（例えば、カウントダウンが 2 分未満の時点で離席検出トリガーをどう計算するか、途中で手動一時停止してから再開した場合に離席時間をどう累積するか、10 秒の猶予期間内に戻ってきた場合をどう計数するか）。

| 実測指標 | 多 Agent ワークフロー（Claude Code） | 単一 Agent（Claude Code） | 単一 Agent（Codex） |
| --- | --- | --- | --- |
| 有効構築所要時間 | 約 101 分 | 約 10 分 | 約 15 分 |
| 4 つの埋め込まれた曖昧性が主動的に質問された | **0/4** | **0/4** | **0/4** |
| 4 つの埋め込まれた曖昧性がテストで固定された | 4/4 | 2/4 | 2/4 |
| 6 つの一般的な UX 欠陥が不具合のまま本番環境へ | サンプル検査 4 種類中 0 種類 | 6/6 | 6/6 |
| テストコード : 製品コード | 約 5:1 | 0.8:1 | 0.9:1 |

（注：多 Agent ワークフローは Codex 上で途中で走行しなくなった——防御的コンテンツが多すぎて積み重なり、エンジニアリングが既に崩壊した——だから表に記載されなかった。）

私は気づいた。AI は明らかにこれらの埋め込まれた曖昧性に気づいていた（多 Agent ワークフローは 4 つすべてをテストに書き込んだほどだ）が、私に質問した回数はゼロだった。さらに、異なるモデルの「静かな判断」の方向が異なっていた：単一 Agent の Codex は 10 秒の猶予期間内での一瞬の戻りを 1 度の中断として計上した；単一 Agent の Claude は最後のキーボード入力（タブを切り替えた瞬間ではなく）から 2 分間の離席計時を開始した。どちらの選択肢のロジックも自己一貫性があるが、誰も私に言わなかった。

この現象をデジタル化基礎の弱い中小企業のビジネスに当てはめると、結果は深刻だ。このような企業の 80% の中核ルールはドキュメントに記載されておらず、すべてベテラン従業員の口の中に存在する（「この種の梱包損傷が品質問題に該当するかは顧客が誰であるかによって決まる」「月末最後の日の注文は古い価格をロックできるか」）。AI に業務管理や内部ツール作成を任せた場合、これらの書き込まれていない空白にぶつかると、AI はエラーを報告せず、相談もしない。それは表情一つ変えずに「シリコンバレー平均常識」セットでお前の代わりに決定を下す。その出力は読みやすく合理的に見え、事実確認（Fact-check）でも幻覚を見つけられないが、ただ会社の習慣に反するだけだ。

しかし、この問題を治そうとしたとき、別の問題に直面した。

Agent に着手前に曖昧性を吐き出させるために、後続バージョンでプロセスに硬いゲートを追加した：開始前に各要件を固定の「7 つのカテゴリ境界スキャンテーブル」（閾値、途中挿入、繰り返しトリガー、時間境界、カウント規則、実行環境、故障復旧）を通す必要があり、ユーザーが各項目を 1 つずつ判断しなければならない。そうでない場合、`gw gate 1` スクリプトは後続タスクの実行を拒否する。

結果として、この一連のルールを実際の複数マイルストーンプロジェクト（最初は 3 つのマイルストーン、39 個のタスクを持つデータダッシュボードの再構築、次は既存製品への自動更新キュータスク追加）に導入した後、Agent は「沈黙を守る」から別の極端に直接ジャンプした：**つまらない疑似問題で KPI を狂ったように稼ぐ。**

プロセスが「境界をすべてリストアップする」ことに報酬を与えるため、タスク計画フェーズに到達すると、PRD 内の境界テーブルは次々と 100 行近くまで膨張した：その大部分は、ビジネスの曖昧性を人間が判断する必要のある問題ではなく、既存のコード呼び出し元を調べたり、データベーススキーマをちょっと見たり、基本的な常識を適用するだけで決定できるエンジニアリング詳細だった。

皮肉なことに、92 行の細かい詳細について相談を求め、最も発言すべき本番操作では再び「沈黙」を選んだ：チームは既に意思決定記録にサーバーサイドがホットリロードをサポートしないと書いてあったのに、6 つのタスク、45 個のサブセッションがすべて完了し、コードがメインブランチにマージされ、Agent たちが夜 10 時半まで残業するまで、メイン Agent は「本番コンテナを再起動できるか」と質問することを思い出した。その時点で、私は既にオフラインになっていた。

最新版では、固定テンプレートの「7 つのカテゴリ境界スキャン」を削除し、実際のビジネスガバナンスに適合した 3 つのルールに置き換えた：

1. **まず家の底を確認し、安易に質問するな**：主 Agent が曖昧性をリストアップする前に、既存の呼び出し元、データベーススキーマ、設定ファイルを読む必要があることを要求する。古いコードに既に答えがある場合は、それに従い、人々を悩ませるために取り出してはならない。（くそっ、結局のところ職人さんと同じようにコード読みをやるハメになるのか。）
2. **1 つの「デフォルト容錯ボトムライン」で 80% の疑似曖昧性を削除する**：テンプレートに直接デフォルト原則を書き込む（例えば「不正なデータに遭遇した場合はスキップしてレポートを記録する；不可逆操作のみハード停止」）。デフォルト原則を適用できるエンジニアリング境界は一切表に記載できず、ユーザーが取得する結果を変更し、先例のないオープンビジネス選択のみ、上司が判断するために持ち込むことが許可される。
3. **本番環境の承認を開始前の（Gate 1）に前倒しする**：「マージ後にサービスを再起動する」というようなリスクがあるが必須の標準アクション、開始前の `Approvals` テーブルでロールバック方法と一緒に一度に署名承認する；承認されない場合、完了時に「サービスは古いコードを実行中」を状態ページの最も目立つ最初の行に貼り付けなければならない。

企業への教訓は一貫している：暗黙的なルールとデフォルトボトムラインを書き込まなければ、AI はお前の代わりに「静かに決定」する；しかし、お前がただ硬い表を使って質問を促すだけなら、それは 90 以上の無意味な言葉で承認者を溺れさせ、その後も最も重要な場所での真の問題を見落とし続ける。

## 二、速さは節約と同じではない

`graph-workflow` の実践的な反復記録を追うと、技術的負債と認知的負債が「テストがすべて緑」という幻想の下でどのようにゆっくり蓄積されるかを見ることができる。

まず、`graph-workflow` の適用対象と実験に GPT シリーズの多 Agent 協作がない理由を説明しよう。Codex 上で基準実験を実行するときに：

- コードの中に Agent が密かに 200 行以上の防御的コンテンツを埋め込み、11 個の不可解な状態フラグ、2 つのバージョンカウンター、3 重リセットロジックを含んでいた。
- 元々要件だった機能の 1 つが、Agent によって静かに削除された。
- Git 呼び出しが常にエラーを報告した後、Agent は自分でスナップショット方式を発明し、ローカルリポジトリを 10 倍以上に拡張した。
- 同じマイルストーンで **66 ファイル、約 24,000 文字** のプロセスドキュメントを一気に吐き出した（すべて GPT の特徴的な防御的定型句）。

Codex 上で多 Agent ワークフローを実行するときに、単にレビュー担当 Agent だけで 145 回のレビューで **1,290 万個の Token** を消費した。

一方、Claude Code は 3 つのマイルストーンで合計 **10 億個以上の Token** を消費し、このうちレビューと仕様チェックが駆動コストの 65% を占めた。

これらの穴を塞ぐために、新しいバージョンでは Coder がハンドオーバー単に「新規防御コード申告フォーム（`Defenses added`）」を記入する必要があり、タスク書（`brief`）に**ハード字数制限**を設定し、テストがコード作成 Agent に歪められないようにするために、テスト作成の Tester をコードベースの外に完全に隔離し、タスク書だけを見てテストをブラインドで作成し、その後外部の密封テストセット（held-out tests）にロックする。

実際の場面では（743 行の製品コードと 3,819 行のテストコードを産出）、これらのいくつかの機械的ゲートが集合的に私に教訓を与えた：

- **「防御コード自己申告」は形式だけ**：6 つのハンドオーバー単の `Defenses added` 欄に整然と `none` と書かれていた。しかし、レビュー Agent が直接コード diff を確認すると、5 つのタスクで少なくとも 7 つの明らかに余分な防御ガードを引き出し、その場で削除した。AI に技術的負債を自分で申告させることは無用で、独立した視点でダイレクトに diff をレビューする必要がある（そのため v0.8 では強制自己申告表を削除した）。
- **ハード字数制限が「文字数削減無限ループ」を引き出した**：タスク 43 は 1 ラウンドのループ記録の書き込み後に字数制限を超え、結果として Agent は字数を制限内に戻すために、そのタスク書を **24 回** も往復して修正した。
- **家の底を見ない「ブラインドテスト作成」は自分で穴を掘っている**：実際の場面で合計 4 ラウンドの正式な返工が発生し、すべてテストまたはタスク書自体が誤って記述されたためで、返工期間中に Coder の製品コードは 1 行も変更されなかった。最も滑稽なタスクでは、Tester が既存のデータベーススキーマを見なかったため、主キーのないテーブルに対して直接 `INSERT OR REPLACE` を書き、実在しないカラムを読もうとした；3 つの密封テストが失敗し、すべてテスト自体のバグで、このために 11 個のテストとレビューサブセッションが無駄に消費された。
- **ダミーフィクスチャ上で全て緑で走った 159 個のテストが、4 つの真の欠陥を漏らした**：すべての自動テストは新しく作成された空のデータベースと 1、2 個の偽テンプレート上で実行され、すべて緑色だった。メイン Agent が最後に本番データベースの副本を使用してページをテストしたとき、4 つの大きな穴が炸裂した：読み取り専用接続が移行されていない古いライブラリにぶつかり、ページは直接開かない；実環境の 11 個のテンプレートを読み込むのは非常に遅い；キューに入った後、リストが更新されない；もう 1 つのボタンは別の言語で書かれていた。

[METR が行ったランダム対照試験](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)では、AI アシスタンスを使用した資深なオープンソース開発者は、実際のタスク完了速度が 19% 遅くなったが、事後にアンケートに記入した場合、誰もが自分たちが 20% 高速化していると一致して感じた。

Agent を使用してコードと計画を作成することは、クレジットカードで分割払いで買い物をするのによく似ている：今すぐに物が手に入り、爽快感が満杯だが、システムに対する理解（認知的負債）は 1 セント も支払っていない。多くの人々は、機械的審査ゲートを何度か追加すれば安心できると思っているが、私の教訓は：機械的ゲートが詰まっているのはほとんど形式で、Agent は大量の Token を消費してお前の形式に合わせる；本番環境の生死を決定するものは、実際のデータコピーと実行インターフェースで肉眼で検査する必要がある。

最後に一言：小規模なプロジェクトや小さな修正については、単一 Agent に「開放的なビジネス選択を判断する」と「ソースコードを見ず、実際の実行インターフェースのみを検収する」を組み合わせた場合、コストは複雑な多 Agent ワークフローの 10 分の 1 で、効果はほぼ同じだ。複数月にわたる大規模プロジェクトまで待つ価値のあるこのステートマシンを備えたワークフローをセットアップする必要がある場合のみ、テストとレビューは実際のデータスキーマと履歴データコピーに直接基づく必要がある。
