## 1. いくつかのシンプルな Skill で、Agent の研究パフォーマンスを高める

2026 年 10 月 20 日、論文 *Automating ML for Science: Can Frontier Agents Climb Scientific Hills in the Wild?* が arXiv で公開された（[arXiv:2610.28763](https://arxiv.org/abs/2610.28763)）。
この論文は 11 の科学分野・20 のベンチマークを対象に、最先端の Coding Agent が各ベンチマークで公表済みの最良モデルを出発点として、それを自律的に改善できるかどうかを調べている。

論文では、Agent に 3 つの Skill を追加している。Research Ideation（研究アイデア出し）、Experiment Management（実験管理）、Scheduled Checklists（定時チェックリスト）だ。追加前後での、20 ベンチマークにおける平均相対改善率は次のとおり。

| Agent | Skill なし | Skill あり |
| --- | --- | --- |
| Claude Opus 4.6（Claude Code） | 10.4% | 20.1% |
| Codex（GPT-5.4） | 4.4% | 8.1% |

論文はさらに、Agent に共通する 3 つの失敗パターンを挙げている。

1. **新規性判断のずれ（Novelty Miscalibration）**：「新しさ」に対する Agent の判断が人間と系統的にずれており、定番の手法をしばしば独創的なアイデアとして扱ってしまう（論文では、コサイン学習率スケジュールをブレイクスルー扱いした例が挙げられている）。
2. **リソースの活用不足（Resource Under-utilization）**：GPU が頻繁にアイドル状態になる、並列で回せる実験を直列で実行する、CPU/GPU の競合を起こす、といった問題。
3. **探索の崩壊（Exploration Collapse）**：実行が進むにつれて戦略がどんどん狭まり、慣れた局所的な最適化に早々と固執してパラメータ調整を繰り返す一方、分野そのものから新しい突破口を探すことはほとんどない。

## 2. 幅広い調査はなぜエンジニアリングの質を上げうるのか

これを日常のエンジニアリングに置き換えると、Agent が状況をよく把握しないまま、いきなりコードを書き始めてしまう、という形で現れる。

私は、コーディングの前に Agent に幅広い調査をさせることで、これを改善できると考えている。

1. **車輪の再発明を減らす**

   Agent はタスクスケジューリングやリトライ、状態管理の仕組みを何時間もかけて実装したものの、その大部分を解決する成熟したコンポーネントがすでにあることを知らない、ということが起こりうる。幅広い調査によって既存の解決策に気づかせ、作業の重心を差別化が必要な部分へ移すことができる。

2. **アーキテクチャ判断の候補を広げる**

   Agent はひとつの案について完全な設計を書き上げることはできても、別の 2 つのアーキテクチャと真剣に比較するとは限らない。先に既存の実践例を調べることで、判断の問いを「この案は実現できるか」から「なぜこの案が他より適しているのか」へ引き上げられる。

3. **隠れたコストを早めに見つける**

   オープンソースプロジェクトの Issues、移行ガイド、セキュリティアドバイザリ、設計に関する議論には、README では強調されていない互換性・性能・保守性の問題が書かれていることが多い。こうした情報は、アーキテクチャレベルのミスを避けるうえで特に役立つ。

4. **モデルの学習データを超えた実践知を得る**

   Agent の内部知識には、あるフレームワークで最近起きた大きな API 変更や、コミュニティがすでに見放した設計パターンが含まれていないかもしれない。検証済みの外部情報は、その判断を更新する助けになる。

ただし、注意すべき点もある。

成熟した解決策が見つかったからといって、それを導入しなければならないわけではない。

私がすすめるのは、そこからアーキテクチャパターンや規約、設計上の知見を学ぶことだ。踏み込むとしても、オープンソースプロジェクトの具体的な実装の細部を参考にする程度にとどめる。

## 3. エンジニアリング向けの Skill をどう設計するか

私はこれを Architecture Discovery Gate（アーキテクチャ発見ゲート）と名付けている。流れは次のとおり。

1. **要件と現在のコードベースを理解する**：まず既存の実装、技術スタック、制約条件を把握する。
2. **外部調査が必要かどうかを判断する**：新規性の高さ、意思決定のリスク、手持ちの知識で足りるかどうかに応じて発動する。
3. **3 種類の情報源を調べる**：
    - 標準と仕様：RFC、公式ドキュメント
    - OSS エコシステム：コード、バージョン、メンテナンス状況
    - 反証：Issues、脆弱性、制約
4. **候補を比較し、ADR に記録する**：「既存のものを再利用する／自分で実装する／現状維持」の 3 つの選択肢のうち、該当するものを少なくとも比較し、ADR（Architecture Decision Record）に判断の根拠を残す。
5. **小規模な検証 → 実装 → 独立したテスト**：実際のエンジニアリング上の証拠で実現可能性を示す。検索結果を正しさの証明として扱わない。

もうひとつ。組織が自前のコードベースを持っているなら、まず社内を調べ、それから外部を調べること。

さらに一歩進めたいなら？

複数の SubAgent に、それぞれ別の答えを探させればいい。

ただし、ここにはひとつ制約を設けることをすすめる。複数の Agent に同じキーワードで検索させ、投票でどの案がいいかを決める、というやり方は避けること。

そうして得られる結果は、たいてい中身がほとんど重複してしまうからだ。

Agent ごとに独立した調査目標を割り当てよう。たとえば上の手順 3 の 3 種類の情報源に対応させて、1 体は標準と仕様、1 体は OSS エコシステム、1 体は反証探しに専念させる。

## 4. 彼女たちを監督なしで競わせてはいけない

以前、ある実験をした。最初は、複数の AI が互いに議論をぶつけ合い、合意に達するまで続ける場を用意しただけだった。

いくつかの試験的なテーマで意外にも悪くない結論が出たので、私は彼女たちにひとつの仕事を任せた。ドキュメントを分類・整理し、レポートを生成するためのドキュメントプラットフォームを作ることだ。

3 社の異なるベンダーのトップモデルが、20 ドルクラスのサブスクリプション 3 つ分の週間利用枠を使い切ったあと（なぜそんなに時間がかかったのかはわからないが、好奇心から彼女たちのお祭り騒ぎを止めなかった）、彼女たちが差し出してきたのは、あらゆる極端なケースを警戒し、完璧な入力がなければ結果を出さず、データの一片ごとに何重ものハッシュ検証を行い、ユーザー操作はすべてコードによる指示で行い、コンテンツをひとつ追加するたびに 3 社の Agent が完全に隔離された 3 つのサンドボックス内でセーフモードのまま意見を出し、投票で決める、炭素系生命体にとことん優しくない金食い虫のポンコツだった。

このドキュメントプラットフォームは、典型的なアーキテクチャの肥大化をたどった。

- ある Agent がデータ整合性のリスクを指摘し、ハッシュ検証が追加された。
- 別の Agent が単一の意思決定点のリスクを指摘し、複数 Agent による承認が追加された。
- 3 体目の Agent が承認プロセスにおけるセキュリティリスクを指摘し、隔離機構が追加された。
- 最終的に、システムのあらゆる部分に十分な技術的理由がそろった。それでも、「ユーザーはドキュメントを整理したいだけなのに、なぜこんなに多くの関門を通らなければならないのか」に答える責任を負う者は誰もいなかった。

理由は単純だ。開発プロセスの中に、あるリスクが解決に値するかどうか、そしてそれを解決するために最大で何を犠牲にしてよいかを決める権限を持つ役割が、ひとつもなかった。

これは一種の特殊なグッドハートの法則（Goodhart's Law）だ。アーキテクチャの正しさ、リスクのカバー率、レビューの一貫性が最適化の目標になると、本当に大切なユーザー価値が少しずつ最適化の対象から押し出されていく。

第 1 節の論文に戻ろう。Research Ideation Skill はタスク開始時に Agent の探索空間を広げ、1 時間ごとに発動する定時チェックリストは、Agent がまた機械的なパラメータ調整に陥っていないかを確認する。論文自身も、これらの Skill は Claude Code の実行軌跡から導かれたものであり、その効果が他のタスクや Agent にそのまま移るとは限らないと認めている。

私たちが論文から学ぶべきなのは、最小限で効果のある行動介入であって、どんどん複雑になる人間社会の統治システムを真似ることではない。

## 5. 今の私のワークフロー

この記事を書いている時点で、私自身の Vibe Coding のワークフローはおおよそ次のとおりだ。

0. **プロダクトの意図と境界**：何を達成したいのか？何はシンプルでなければならないのか？何はひとまず放っておくのか？
1. **調査**：Main Agent がプロジェクトの段階、既存の技術スタック、納品範囲を確認し、同時に Research SubAgent を 1 体送り出して、既存の解決策、メンテナンス状況、エンジニアリング上の知見を調べさせる。
2. **技術案の比較とアーキテクチャの決定**：私と Main Agent で決める。プロダクトの目標を優先し、依存関係と複雑さを抑える。
3. **詰問タイム**：Skeptic SubAgent が、範囲を区切った反対意見を出す。
4. **リリース判断**：操作の流れが最後まで通るかを確認し、リリースできるかを判断する。

だからこそ、Agent に最初の一行を書かせる前に、まず「調べる」ことを覚えさせよう。
